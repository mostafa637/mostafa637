## Architectural facts retained for implementation

- XSAVE, XSAVEOPT, XSAVEC, and XSAVES use the implicit EDX:EAX 64-bit request mask. The requested-feature bitmap is RFBM = XCR0 AND EDX:EAX for XSAVE/XSAVEOPT/XSAVEC. XSAVES additionally ORs IA32_XSS with XCR0 before applying the mask; this pure-Go state currently has no IA32_XSS model, so XSAVES needs an explicit conservative policy.
- The destination is memory-only and must be 64-byte aligned architecturally. The JIT memory model should validate the effective address before writing; the operation does not change arithmetic flags.
- XSAVE and XSAVEOPT use the standard extended format. XSAVEC and XSAVES use the compacted extended format and set XCOMP_BV bit 63, with the lower bits describing the requested compacted components.
- XSAVE/XSAVEOPT update only the XSTATE_BV field according to the old header and XINUSE/RFBM; XSAVEC writes the saved-component bitmap and XCOMP_BV. In this emulator the available state is x87, SSE/XMM, MMX, FCW/FSW, and XCR0, with no MXCSR field yet.
- The legacy XSAVE region is 512 bytes and the XSAVE header starts at offset 512; the header consumes 64 bytes, so the extended area begins at offset 576. Standard SSE state is represented in the legacy region; the current MachineState64 has XMM and x87 register data but lacks a complete architectural MXCSR and x87 80-bit/tag-word image.
- XSAVE saves x87 when requested feature bit 0 is active and XMM when SSE bit 1 is active. MXCSR/MXCSR_MASK are also part of the SSE area, but the current state model must choose explicit defaults until MXCSR is added.
- XSAVEOPT may omit components under init/modified optimizations; for deterministic emulation, writing the complete requested legacy component while preserving header rules is acceptable, but the implementation must not silently claim unsupported feature components.
- XSAVEC/XSAVES compacted offsets depend on CPUID leaf 0xD component sizes. With only x87 and SSE modeled, a compacted implementation can keep the legacy region and header exact and avoid unsupported component payloads; if AVX or supervisor state is requested, the JIT should reject or trap rather than fabricate offsets.
- Felix Cloutier labels its pages unofficial and mechanically separated; Intel SDM remains the normative source. The implementation should keep this file as a semantics reference, not as executable instructions.

## Current MachineState64 mapping

- `XMM [16][16]byte`
- `MMX [8]uint64`
- `FP [8]fpu.Value`
- `FSW uint16`, `FCW uint16`, `XCR0 uint64`
- No `MXCSR`, `MXCSR_MASK`, x87 tag word, FPU instruction/data pointers, or IA32_XSS field currently exist.

## Design consequence

Before claiming full XSAVE support, add an explicit xstate serialization layer and a conservative supported-feature mask. The first safe increment should implement standard-format XSAVE/XSAVEOPT for the modeled x87/SSE legacy region, with strict 64-byte alignment and memory fault propagation. XSAVEC/XSAVES should share the header logic but must not serialize unsupported compacted components as if they existed.

## Legacy FXSAVE64 map used by this implementation

Source: https://www.felixcloutier.com/x86/fxsave

- In 64-bit mode with REX.W, the legacy 512-byte region uses FCW at offset 0, FSW at 2, abridged FTW at 4, FOP at 6, 64-bit FIP at 8, 64-bit FDP at 16, MXCSR at 24, and MXCSR_MASK at 28.
- ST0..ST7/MM0..MM7 occupy 80-byte slots at offsets 32 + 16*i; each slot contains 10 meaningful little-endian bytes and six reserved bytes.
- XMM0..XMM15 occupy 16-byte slots at offsets 160 + 16*i.
- Bytes 416..463 are reserved and bytes 464..511 are available to software; the serializer initializes them to zero.
- The abridged FTW stores one valid bit per physical register, so the emulator's FTW byte is serialized directly.
- XSAVE's standard format keeps this 512-byte legacy region and places the 64-byte XSAVE header at offset 512.
